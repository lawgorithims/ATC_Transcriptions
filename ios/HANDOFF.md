# Obelisk — Session Handoff

Pick up the **Obelisk** iOS app (on-device ATC transcription) in a fresh session without losing
context. Pairs with `RECOVERY.md` (rebuild the ship box) and the Claude **memory notes** (which hold
the secret IDs and box details — this repo is **PUBLIC**, so nothing secret lives here).

> ⚠️ **Public repo.** Do NOT commit secrets, App Store Connect key IDs, the `.p8`, or the build-box
> host/IP. Those live in the memory notes named below and on the build box.

---

## 1. What this is

- **Obelisk** — universal iPhone/iPad SwiftUI app, fully on-device ATC radio transcription.
  Fine-tuned Whisper via **WhisperKit** (CoreML/ANE) + a two-tier corrector (deterministic + an
  optional CPU llama.cpp / Apple-Foundation LLM) + RAG context. Sources: internet LiveATC feed,
  device mic, USB audio, replay demo.
- Repo: **`lawgorithims/ATC_Transcriptions`** (local dir is `ATC_Transcribe`). Work on **`main`**.
  All app code is under `ios/ATCTranscribe/`. The Xcode project is generated by **xcodegen** from
  `ios/project.yml` (no checked-in `.xcodeproj`).
- App Store Connect app **Obelisk**, bundle `com.flycommsight.atctranscribe`. **Builds 1–8 shipped
  to TestFlight on 2026-06-27**; current `main` is the build-8 state.

## 3. Build / test / ship loop (the actual cadence used all session)

The build box (a headless Scaleway M4 Mac, `User m1`) has Xcode, the models, and the vendored
`llama.xcframework`. Local edits on Windows; **nothing compiles on Windows**.

**Iterate (sync changed files → build/test):**
```bash
# from ios/ on the Windows box, tar the files you changed to the M4 (no --delete; never touch
# Resources/Models or Vendor):
tar czf - ATCTranscribe/UI/Foo.swift ... | ssh m1@<host> 'cd ~/ATC_Transcribe/ios && tar xzf -'
# on the M4: regen + test against the BOOTED simulator (id from `xcrun simctl list devices booted`):
export PATH="$HOME/.xcodegen/xcodegen/bin:$PATH"
xcodegen generate
xcodebuild -project ATCTranscribe.xcodeproj -scheme ATCTranscribe \
  -destination 'platform=iOS Simulator,id=<BOOTED_SIM_ID>' \
  -derivedDataPath /tmp/dd-obelisk CODE_SIGNING_ALLOWED=NO test
```
- Adding a **new .swift file** requires `xcodegen generate` before `xcodebuild` (globs at gen time).
- `git reset --hard origin/main` on the M4 is the safe way to put it on an exact commit before
  shipping (Resources/Models + Vendor are untracked/ignored and survive the reset).

**Ship to TestFlight (outward-facing — only when the user asks):**
```bash
# on the M4, in ios/, with the ASC env from the memory note + the NEXT build number:
ASC_KEY_ID=... ASC_ISSUER_ID=... ASC_KEY_PATH=/Users/m1/AuthKey_*.p8 TEAM_ID=... \
BUILD_NUMBER=9 bash Tools/ship_testflight.sh
```
`ship_testflight.sh` is the **headless-correct** recipe (archive UNSIGNED → sign-for-distribution at
export). `Tools/testflight.sh` does NOT work over SSH. **LEAN=1** (default) ships model-less; the app
downloads models on first launch from HuggingFace (`SingularityUS/atc-whisperkit`).

**Version gotcha (fixed build 3+):** `project.yml` info binds `CFBundleVersion=$(CURRENT_PROJECT_VERSION)`
and `CFBundleShortVersionString=$(MARKETING_VERSION)` (=1.0). Without that, xcodegen baked a literal
`1` and uploads collided. Builds ship as `1.0 (N)`.

## 4. Working practices that worked well

- **Cadence:** edit → sync → `xcodebuild test` on M4 → fix → commit to `main` → `reset --hard` M4 →
  `ship_testflight.sh BUILD_NUMBER=N`. Each batch = one build.
- **Adversarial review before every ship.** Run a `Workflow` that fans reviewers across dimensions
  (concurrency, SwiftUI, DSP, regressions) then adversarially verifies each finding against the code.
  This caught real HIGH bugs every batch (audio-session leaks, an AVAudioEngine re-attach crash, a
  mic data race, a hallucination-filter resurrection, a per-segment decode blowup). **Keep doing it.**
- **Tests:** unit + XCUITest on the Simulator. `test1_onboardingGateAndSkip` XCTSkips when a model is
  bundled (the gate only shows on lean builds) — that 1 skip is expected. The **neural path** (real
  ANE) is validated by the macOS `ATCKitProbe` (`Tools/probe.sh`), NOT the Simulator (no ANE there).

## 5. Architecture map (key files)

- `Engine/LivePipeline.swift` — actor: source chunks → VAD → **diarize** → preprocess → transcribe →
  correct → `TranscriptRecord`; runtime setters (`setCorrector/LLM/Gate/Squelch/Diarization`).
- `Engine/TranscriptionSession.swift` — @MainActor ObservableObject wrapper; owns audio-session
  teardown on stop/natural-end; `inputLevel`.
- `UI/AppModel.swift` — the view-model (sources, model switching, standby, squelch, diarization,
  showDebug, widgets, onboarding gate). `start()/beginCapture()` (mic permission + session activate).
- `Audio/` — `AudioSource` (mic/USB/replay), `StreamAudioSource` (LiveATC MP3 decode),
  `AudioSessionManager`, `AudioMonitor` (live-feed speaker monitor), `VADSegmenter`, **`Diarizer`**.
- `Core/` — `ATCCorrector` (deterministic + **HallucinationFilter** + chain), `RepetitionCollapse`,
  `LocalLLMCorrector`/`FoundationModelsCorrector`, `ConfidenceGate`, RAG (`ATCKnowledge*`).
- `UI/` — `ConsoleView` (top bar, controls, input meter, standby banner, `SquelchControls`),
  `TranscriptView` (rows + speaker chips + amber correction highlight), `SidebarView` (customizable
  widgets incl. `DiagnosticsCard`), `SettingsSheet`, `Theme` (blue accent), `DeviceLoad` (CPU/thermal).
- `Download/` — `ModelCatalog`, `ModelDownloadManager`, `OnboardingDownloadView` (first-run gate).

- ~~**The integrity monitor deleted the aeroplane on an ordinary signal dip.**~~ — DONE (2026-11-06).
  `shouldSuppressOwnship` was `state >= .unreliable`, and `.unreliable` means accuracy past 100 m or a
  fix 30 s late while moving — neither is evidence the position is WRONG, only that it is COARSE. One
  such reading removed ownship, the track, the glide ring, terrain AGL and the storm alert at once.
  Three changes: (a) the one property became two — `isTrustedForGuidance` (`< .unreliable`, for a
  glidepath and the georeferenced plate) and `isPositionProbablyReal` (`< .suspect`, for anchoring a
  clearance); the map gates on neither and always draws. (b) `Config.confirmUnreliableCount = 3` —
  three consecutive observations before `.unreliable` is published, held at `.degraded` until then;
  escalation only, clearing is immediate; NOT applied to `.suspect`, which is already pair-based and
  latched. (c) The banner is dismissible, keyed to the state acknowledged so anything worse still
  announces (`AppModel.showsIntegrityBanner`). ⚠️ The amber/red ownship symbols and the 1-sigma
  accuracy ring already existed in `ChartMapView.ownPlane(for:)` and `syncAccuracyRing` — they were
  unreachable, because the only states they were drawn for were the states that removed the symbol.
  Demonstrate it with `--force-gps-integrity nominal|degraded|unreliable|suspect` (DEBUG only), which
  pins the published verdict — applied in `DeviceLocation.forced(_:)` at the single publication point,
  NOT inside the monitor, because the flight-simulator path builds its own assessment and never
  reaches the detectors, so a monitor-side pin could not be used with `--hold-ownship`. A pinned
  verdict carries `isSimulatedVerdict` and the banner shows a FORCED chip, so it can never be mistaken
  for a real one. Verified: `--hold-ownship 42.5 -77.0 8000 90 140 --force-gps-integrity unreliable`
  draws the red aeroplane, reports AGL, and the banner dismisses without taking the symbol with it.
- ~~**A crash cost the whole logbook track and stopped the recording.**~~ — DONE (2026-11-06). The
  trail was ALREADY being written to disk and `recoverOnLaunch` was already reloading it; what was
  missing was anything that READ the `.recovered` state. Nothing did — the whole branch was dead. So
  the pilot saw a REC button reading "not recording" over a recovered trail, pressed it, and
  `startRecording` called `resetAccumulators()` and then persisted the empty recording over the file:
  the recovery destroyed what the crash had spared. Four changes: (a) `RecoveredRecordingBanner` in
  the console stack offers **Resume** or **Save** (no Discard — dismissing is the only irreversible
  action on that bar, and Save puts it somewhere deletion is deliberate); (b) `startRecording` now
  refuses while `.recovered`; (c) `stopRecording` accepts `.recovered` and ends the flight at its LAST
  BREADCRUMB, not `Date()`, so the hours the app spent shut are not logged as flight time; (d)
  `persistEverySec = 20` beside the every-10-points rule, because a parked or slow aircraft only
  appends on the 15 s heartbeat and ten points was 2½ minutes of exposure. ⚠️ `ConsoleView` observes
  the recorder with its own `@EnvironmentObject`: `FlightRecorder` is a NESTED ObservableObject, so
  `model.flightRecorder.recovered` would compile, render once and never update. `FlightRecorder(directory:)`
  is injectable so `FlightRecorderRecoveryTests` never touches a real pilot's in-progress flight.
  A second, independent contributor to "it stopped recording": `currentBreadcrumbFix()` gates on
  `presentPosition`, which returned nil on a degraded fix — so the trail stopped whenever the GPS
  monitor cried wolf. Fixed by the integrity change above.
- ~~**A flight may not save when the record button is pressed again.**~~ — DONE (2026-11-07). The
  swipe hole was closed earlier (the save sheet is `interactiveDismissDisabled`, because a swipe
  cleared `pendingLoggedFlight` without calling save or discard and the flight reappeared at the
  NEXT launch, reading as the logbook having dropped it). What remained was that the app never SAID
  anything, plus two real data holes found while finishing it:
  1. **A stop that caught no fix was mute.** `buildFlight` returns nil on an empty trail,
     `toggleFlightRecording` set `pendingLoggedFlight = nil`, and no sheet appeared — so the pilot
     could not tell a saved flight from an empty one. That is the whole of the reported doubt.
  2. **⚠️ PRESSING REC OVER A RECOVERED RECORDING ALSO DID NOTHING, SILENTLY** — a silence the
     crash fix itself created. `startRecording` refuses over `.recovered` (that guard is what stops
     the first REC tap destroying the recovered trail) and returned without a word, so the fix for
     losing the flight looked, from the cockpit, like a dead REC button.
  3. **⚠️ A KILL WINDOW THAT LOST THE FLIGHT OUTRIGHT.** `stopRecording` deleted the active mirror
     BEFORE writing the finished flight, so a kill between the two left neither file — on the one
     action a pilot takes believing their flight is now safe. The order is reversed; the worst case
     is now both files existing.
  4. **⚠️ WHICH THE REORDER MADE POSSIBLE: both files at once.** `recoverOnLaunch` now prefers the
     finished flight and deletes the stale mirror. Without that the pilot would get a save sheet AND
     a "resume this flight" banner for the same flight, and resuming would append fresh points to a
     trail finished minutes ago — one flight logged twice, the second one wrong.

  had: one slot, no queue, newest wins, auto-dismissing. ⚠️ NEVER USE IT FOR ANYTHING NEEDING AN
  ANSWER — it leaves on a timer, so decisions and unsaved data stay in the banner stack
  (`RecoveredRecordingBanner` is deliberately not a toast). Used for the two silences above and to
  confirm both outcomes of the save sheet. `AppModel.flightRecorder` is now injectable, which also
  closes a latent hazard: a default `FlightRecorder` reads the app's real Application Support
  folder, so any `AppModel()` test shared a directory with a pilot's in-progress flight.
  15 tests across `FlightRecorderRecoveryTests` and the new `LogbookSaveFeedbackTests`. Verified on
  an iPhone: REC, REC again with no GPS → the amber capsule appears above the GPS bar.
- ~~**Ownship motion is jerky, and the glide bands move independently.**~~ — DONE (2026-11-06). Two
  causes, both in the MapLibre engine (MapKit was never as bad: `MKAnnotation.coordinate` is
  `@objc dynamic` and MapKit glides the view between values; a shape source has no equivalent).
  (a) `updateOwnship` wrote `src.shape = f` — a teleport — once per delivery, and `DeviceLocation`
  runs a 15 m `distanceFilter`, so on a 0.5 NM chart the aeroplane advanced a dozen points at a time.
  (b) ONE signature gated the symbol and the accuracy ring together, and it carried `qJit` (~12 m dead
  band) and `qDeg` (3°). Those exist for the RING — a 64-point polygon that must not rebuild for a
  metre of jitter — but they also stopped the aeroplane moving under 12 m or turning under 3°.
  Fix: `Core/OwnshipMotion.swift` dead-reckons the last fix forward along track at ground speed AND
  eases the drawn position toward that estimate (smoothing only the second still steps once per fix;
  only the first trades small regular steps for occasional large ones). A `CADisplayLink` at 30 fps
  renders the symbol alone; the ring keeps its dead band. ⚠️ Bounds, because this draws the aeroplane
  where the receiver has not said it is: `maxExtrapolationS = 2` (a lost signal must not fly the
  symbol onward on a stale heading), `minSpeedKt = 15` (below that GPS course is noise and a parked
  aeroplane would wander), both track and speed required, and `snapDistanceNm = 0.25` so a reposition
  is taken instantly instead of crawling across the chart. The link skips the source write entirely
  when nothing moved by 0.5 m and the course is unchanged, so idle costs nothing.
  The glide bands now SLIDE from `LZRiskController.energyAnchor` (where the 5 s sweep was computed) to
  where the symbol is drawn, re-slid on movement of `bandSlideNm = 0.02` (~37 m, ≈2 Hz at 140 kt,
  never when parked). ⚠️ Sliding is an approximation — the terrain under the new position is not what
  the rays were marched over — but it is a STRICTLY SMALLER error than before, when the footprint was
  both stale and in the wrong place; this fixes the second. Shortening the 5 s sweep is a battery
  decision, not a rendering one. NOT VERIFIED IN MOTION: the Simulator's held ownship does not move,
  so smoothness itself was not watched — the interpolation maths is pinned by `OwnshipMotionTests`.

- ~~**Route labels drift during a pan** at large zoom-outs instead of staying with their route.~~ —
  DONE (2026-11-07). `airways-label` used `symbolPlacement = "line-center"`.
  ⚠️ THE GEOMETRY WAS NEVER THE PROBLEM, which is why this looks like a one-line fix for a
  confusing symptom. `Airways.inRegion` selects idents whose vertices fall in the camera box but
  hands back WHOLE runs, never clipped — so each feature is stable as the pilot pans. MapLibre,
  however, tiles a shape source internally, and "line-center" resolves to the centre of each
  tile-clipped piece; re-tile on a pan and that centre moves, so the ident walks along its airway.
  Now `"line"` with `symbolSpacing = 260`, which places labels at intervals ALONG the geometry
  instead of at one computed point. Stable under re-tiling, and it is also what a sectional does:
  an airway carries its ident repeatedly so it can be read wherever you are looking, not only at
  the midpoint of a run. Verified over Philadelphia at wide zoom — J110, V252, Q75, Q437, T459,
  Q409, V166 all sit on and rotate with their lines across a pan.

**⚠️ RUNNING XCUITEST ON A SHARED MAC — read this before trusting a UI-suite result.**

Two sessions lost hours to this on 2026-11-07. Concurrent XCUITest runs on one Mac can kill each
other at RUNNER BOOTSTRAP, and the failure does not say so.

IT WEARS THREE MASKS, and only the first is obviously a harness problem:
1. `Executed 0 tests` for every class, `TEST FAILED`, and no failure named anywhere. The log is
   ~80 lines and the real line is `ATCTranscribeUITests-Runner encountered an error (Early
   unexpected exit, operation never finished bootstrapping — Test crashed with signal kill before
   establishing connection.)`.
2. `Mach error -308 - (ipc/mig) server died`, 0 tests executed.
3. ⚠️ THE DANGEROUS ONE: unrelated tests "fail" with waits timing out — an airport card that
   never opened, a theme menu not hittable — ending in `FBSOpenApplicationServiceErrorDomain
   Code=4, "Application info provider returned nil"`, i.e. the app left the device mid-run. Those
   named failures are NOT REAL; the same tests passed on the next run. Someone who only knows mask
   1 will take mask 3 at face value and go hunting in the product code.

IT IS NOT "TWO RUNS ALWAYS DIE". A full iPad Pro 13-inch suite completed clean (68 / 13 skipped /
0 failures) during the same window in which two iPhone runs were being killed. The pattern fits
"whoever is mid-bootstrap while another run is active tends to lose" rather than a blanket rule —
so do not write this off when you see a suite survive contention once.

BEFORE A UI RUN, check nobody else is on the machine:
`ps -eo pid,etime,command | grep '[x]codebuild ' ` and `xcrun simctl list devices booted`.
Other Claude sessions show up with their own `-derivedDataPath`, which identifies whose run it is.

⚠️ NEVER `xcrun simctl shutdown all` ON THIS MACHINE. It reaches other sessions' devices and will
shut down a stranger's simulator mid-test — that happened on 2026-11-07 and silently invalidated a
third session's run. Shut down only the device you booted, by UDID, the way `uitests.sh` already
does with its own `$SIM`.

ALSO: `TaskStop` on a backgrounded `xcodebuild` kills the shell, not necessarily `xcodebuild`
itself. Check `ps` after stopping one, or the orphan keeps driving the simulator.

**Thunderstorm alert (`Core/ConvectiveAlert.swift`) — what it now reads, and what is still open.**

The alert is **source-agnostic**: it consumes `ConvectiveCell`s, and four products supply them, because
no one product answers the whole question. `ConvectiveCellMerge` folds them into one list — identity to
the highest-ranked source (the name a controller would use), every number to whichever source has the
conservative one.

| source | polygon | tops | motion | file |
|---|---|---|---|---|
| Convective SIGMET (AWC) | area | stated | stated | `Hazards/ConvectiveSigmetService.swift` |
| Center Weather Advisory | smaller area | **text only** | **text only** | `Hazards/CWAParser.swift` |
| NWS Severe Tstm Warning | one storm | **none** | stated, recent | `Hazards/SevereWarningParser.swift` |
| MRMS echo tops | one storm, measured | **measured** | derived | `Hazards/MRMSEchoTopService.swift` |

MRMS closes the gap the bulletins leave: a Convective SIGMET needs ~40% coverage, a line, or a severe
cell, so an isolated ordinary thunderstorm can be reported by nobody. Verified end to end on 2026-11-04
against a 59,055 ft echo top at 26.87/−97.58 that **no** Convective SIGMET covered.

Three things found by measurement that a future session should not have to rediscover:

1. **MRMS is small.** The CONUS `EchoTop_30` grid is **364 KB** gzipped (an earlier note here ruled MRMS
   out on size and was wrong by an order of magnitude). Discovery is a **1.4 KB** S3 listing using
   `start-after` on the NOAA Open Data mirror, because keys sort chronologically.
2. **The only format blocker was GRIB2 template 5.41** (PNG payload). `PNGGrayRows` decodes it
   **row by row** rather than through ImageIO, because the CONUS bitmap is 49 MB and the window needs
   ~0.5 MB of it; the decode stops at the southern edge of the window. Measured 96 ms for a 4° box.
3. **Centroid tracking of threshold blobs does NOT give storm motion.** Tried first; against two real
   frames inside Convective SIGMET 7C (bulletin: MOV FROM 270 at 20 kt) it returned FROM 031 @ 51 kt,
   FROM 044 @ 66 kt and FROM 232 @ 59 kt — scattered through all four quadrants, because a 23 NM blob's
   centroid wanders further than the storm translates. Replaced by whole-field cross-correlation
   (`RadarCellFinder.fieldMotion`), which agreed with four independent bulletins to within 13°.

**OPEN — in rough value order:**

- **Derived motion reads 20–25% SLOW**, every time, measured against four bulletins. It is structural:
  maximising overlap anchors on the persistent core while only the flanks translate. Currently paid for
  with a wider drift allowance (`ConvectiveAlert.radarDriftErrorFraction = 0.40`) rather than a fudge
  factor on the speed. A proper fix is per-cell TREC with sub-pixel peak interpolation.
- ~~**Overflight clearance uses the AIM's 5,000 ft FLOOR**~~ — DONE (2026-11-04). The full rule is
  applied: `ConvectiveAlert.requiredClearanceFt` takes the greater of the 5,000 ft floor and 100 ft per
  kt of wind at the cell's own top, sampled from the held GFS field by `WindFieldSet.windAt`. Two things
  to know before changing it. (a) **The wind may only raise the bar** — nil, calm, stale or
  outside-the-box all return the floor, which is the behaviour the alert had before; every absent-wind
  path can therefore stay a plain `nil`. (b) **The fetch is no longer tied to the wind overlay**:
  `AppModel.stormAlertNeedsWind` enables `WindAloftService` whenever a storm alert has a live cell,
  because `showWindAloft` defaults OFF and the rule would otherwise be dead on a fresh install. Fetching
  does not draw — the particle layer is gated separately. Measured live on 2026-11-04 12z+7h over
  22–42N/113–78W: of the six live Convective SIGMETs, every top sat in 28–46 kt, so the rule asked for
  the floor at all six — but 41% of the box at 31,000 ft and 51% at 39,000 ft were over 50 kt (peaks of
  114 and 118 kt, which ask for ~11,500 ft), so it binds often, just not wherever storms happen to be.
  What is still missing: **nothing tells the pilot the rule is running on an OLD wind** — `freshFieldSet`
  refuses a stale run and the banner then silently reverts to the floor.
- **The layers panel is ~2,000 pt of prose and has no scroll affordance.** Every live layer carries an
  explanatory note while it is ON, so on a 13-inch iPad the overlays column is about two and a half
  screenfuls and the clipped edge looks like the end of the list. The popover cap has been raised twice
  (460 → 860 → 1,100) chasing it, and each raise was forced by a UI test finding a row that had dropped
  below the fold — the second time as three silently dropped taps that read like a dead binding. The cap
  is now "as much as the device will give"; the remaining fix is editorial, not geometric. The map-overlay
  change below is the first one to pay that back rather than borrow against it: it needed a clause about
  what it draws, and took the clause out of the convective note's own word count (the GFS parenthetical
  and the spelled-out product names), leaving the panel shorter than it found it. Do the same.
- ~~**No map overlay.**~~ — DONE (2026-11-04). `UI/ConvectiveMapLayer.swift` holds the engine-independent
  geometry (`ConvectiveCellDraw`) plus the classic engine's reconcile; the MapLibre half is
  `updateStormCells` / `stormFeatures` in `MapLibreChartView`. Each cell draws as an outline, a motion
  arrow and a tops/base block, bold-and-filled for the cell the banner is warning about and a thin wash
  for one merely known. Five things to know before changing it:
  (a) **The ring is advanced to `AppModel.convectiveDrawAt`, not to `Date()`** — to the instant the alert
  last reasoned, so the outline and the banner cannot contradict each other, and so the diff signature
  does not change on every pass (it would, and sixty-four polygons would be rebuilt per second).
  (b) **`convectiveDrawCells` is the MERGED list, not the dismiss-filtered one.** The X silences the
  banner, not the weather; a dismissed cell keeps its outline and loses only the emphasis.
  (c) **There is no layer toggle** — the list is empty unless a storm-alert source is on and found
  something, and the alert's own toggles are already in the Map-layers panel.
  (d) **The hue is `MapTheme.convective` (teal), and it was violet first.** Reusing the EONET storm
  violet looked obviously right and read as a MOA on a sectional. The argument is on that theme field.
  (e) A two-point **LINE TS** draws as a line, not a dropped polygon — it is a squall line, the most
  dangerous shape in the feed.
  (f) **The cells are tappable** (2026-11-05). `ConvectiveCellDraw.contains` / `.containing` / `.object`
  answer the probe, and `MapObjectKind.convective` sorts ABOVE a live TFR in `MapProbe.merge` — weather
  that can destroy the aircraft over a boundary that merely forbids it. Three things there:
  the hit test is the ring **as drawn**, not as issued (a 20-minute-old cell at 45 kt is fifteen miles
  from its bulletin, so testing `cell.polygon` would answer for an outline that is not on the screen);
  a 2-point LINE TS has no interior, so each engine reaches it by ON-SCREEN distance instead
  (`stormCandidates`), which is how the airway layer has always made a line tappable; and the card's
  verdict comes from `AppModel.convectiveThreat(for:)`, which re-runs the alert for one cell when the
  banner's capped list has no record of it — `ConvectiveAlert.threats` returns only `maxThreats`, so the
  fifth cell of a squall line would otherwise read "no warning raised" over a penetration. The card also
  offers **Restore this warning** for a dismissed bulletin, which was a one-way door before.
  Not done: the experimental standalone MapLibre harness at the bottom of `MapLibreChartView.swift` does
  not feed the layer — only the shipping `MapHostView` path does. `--demo-storms` seeds three cells (one
  of each kind) on the KBOS→KORD corridor; pair it with `--hold-ownship 42.5 -77.0 39000 270 300`, or
  with `--hold-ownship 41.19 -78.25 39000 270 300` to sit on the squall line. ⚠️ `-atc.map.engine.maplibre
  NO` does NOT select the classic engine: the argument domain stores "NO" as a STRING and the model reads
  `object(forKey:) as? Bool`, which yields nil and falls back to the default (MapLibre). Use `0`/`1`, or
  the toggle in Settings → General → Map engine, and check the toggle before believing which engine ran.
- **MESH (hail) is 30 KB on the same cadence** and would give radar cells a real severity instead of
  nil. Cheap, not wired.
- **CONUS only.** Convective SIGMETs are CONUS + coastal waters; the MRMS CONUS grid likewise. MRMS also
  publishes ALASKA and CARIB domains, which the decoder would handle unchanged — only the product paths
  and a domain choice are missing.
- **No FIS-B.** The Stratux integration is GPS/traffic only. FIS-B would give NEXRAD and lightning with
  no internet at all, which matters when cellular dies at altitude. Not investigated beyond confirming
  the current link does not carry it.
